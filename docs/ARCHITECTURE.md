## Η κεντρική αρχιτεκτονική απόφαση

**Ο πυρήνας της επιχειρησιακής λογικής δεν γνωρίζει ότι υπάρχει HTTP ή βάση
δεδομένων.**

Το `app/core/` δέχεται απλές δομές δεδομένων και επιστρέφει απλές δομές
δεδομένων. Ο χρόνος περνάει ως όρισμα, ποτέ ως `datetime.now()`.

Οι συνέπειες είναι πρακτικές, όχι θεωρητικές:

| Συνέπεια | Μέτρηση |
|---|---|
| Τα tests τρέχουν χωρίς βάση δεδομένων | 68 tests σε 0.9 δευτ. |
| Τα tests είναι ντετερμινιστικά | Καμία εξάρτηση από ρολόι |
| Το pipeline μένει γρήγορο | Στάδιο 2 < 1 λεπτό |
| Η λογική δοκιμάζεται εξαντλητικά | 100% κάλυψη στον πυρήνα |

Αν ο αλγόριθμος συνάθροισης ήταν γραμμένος μέσα σε ένα endpoint, κάθε test θα
απαιτούσε βάση, HTTP client και ελεγχόμενο ρολόι — και θα είχαμε γράψει πέντε
tests αντί για τριάντα.

## Στοίβα και αιτιολόγηση

| Επίπεδο | Επιλογή | Γιατί | Τι απορρίφθηκε |
|---|---|---|---|
| Frontend | React + Vite + TypeScript | Γρήγορο build στο CI· στατικά αρχεία που σερβίρει το ίδιο container | Flutter Web — περιττά βαρύ CI για μία web εφαρμογή |
| Backend | FastAPI + Pydantic | Αυτόματο OpenAPI schema, χρήσιμο ως τεκμηρίωση API στο παραδοτέο | Django — ο ενσωματωμένος admin και το ORM θα έδεναν τη λογική στο framework |
| Πυρήνας | Καθαρές συναρτήσεις | Βλ. παραπάνω | Λογική μέσα σε services με dependency injection — υπερβολή για αυτό το μέγεθος |
| Βάση | PostgreSQL + SQLAlchemy + Alembic | Δωρεάν instance στο Render· migrations με ιστορικό | MongoDB — τα δεδομένα είναι σχεσιακά και οι συναθροίσεις απαιτούν joins |
| Tests | pytest + coverage | Παραμετροποιημένα tests, αναφορά κάλυψης για screenshot | unittest — περισσότερος θόρυβος για το ίδιο αποτέλεσμα |
| Packaging | Docker multi-stage | Ένα image, ίδιο τοπικά και στην παραγωγή | Απευθείας deploy πηγαίου κώδικα — δεν αποδεικνύει Continuous Delivery |
| CI/CD | GitHub Actions | Δωρεάν, στο ίδιο repo, ευανάγνωστα screenshots | Jenkins — απαιτεί δικό του server· GitLab CI — θα σήμαινε μεταφορά του repo |
| Hosting | Render free tier | Δέχεται Docker image με deploy hook· PostgreSQL στο ίδιο περιβάλλον | Vercel — εξαιρετικό για frontend, απαιτεί χωριστή λύση για το backend· Heroku — δεν έχει πλέον δωρεάν βαθμίδα |

## Μοντέλο δεδομένων

```
User ──1:N──> Report ──N:1──> Line ──1:N──> Stop
 │                │
 │                └──1:N──> Confirmation
 └──1:N──> Confirmation
```

- **User** — `email`, `password_hash`, `role` (`passenger` | `operator`),
  `confirmations_received`, `disputes_received`
- **Line** — `code` (π.χ. «550», «Μ3»), `name`, `mode` (`bus` | `metro` | `tram`)
- **Stop** — `name`, `line_id`
- **Report** — `line_id`, `author_id`, `delay_minutes`, `category`, `created_at`
- **Confirmation** — `report_id`, `user_id`, `agrees` (bool), `created_at`

Ο βαθμός αξιοπιστίας **δεν αποθηκεύεται**· υπολογίζεται από τα σωρευτικά πεδία
του χρήστη τη στιγμή της συνάθροισης. Έτσι μια αλλαγή στον τύπο υπολογισμού
ισχύει αναδρομικά χωρίς migration.

## Θέματα που εκκρεμούν

- **Caching της εκτίμησης.** Προς το παρόν η συνάθροιση εκτελείται σε κάθε
  αίτημα. Με το μέγεθος δεδομένων της εργασίας είναι αμελητέο κόστος·
  καταγράφεται ως γνωστός περιορισμός αντί για πρόωρη βελτιστοποίηση.
- **Πραγματικά δεδομένα GTFS.** Στη Φάση 2 χρησιμοποιείται seed αρχείο με
  υπαρκτές γραμμές, όχι ζωντανή σύνδεση σε open data.
